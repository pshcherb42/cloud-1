1. The big picture

The subject asks for a WordPress website that puts itself onto a brand-new, empty Ubuntu server with one command.

Think of opening a restaurant, and wanting an identical one in any city within an hour:

In the analogyIn this project
The restaurantThe website: WordPress, its database (MariaDB), and phpMyAdmin (a web page to look at the database)
The empty buildingA server: a computer that is always on and connected to the internet. For now two practice servers on your laptop; later rented ones on AWS
The instruction manualThis repository (the files in the cloud-1 folder)
The manager who follows the manualAnsible, a program on your Mac that connects to the servers and follows the manual
Why not just log in and set the server up by hand? 1) You forget what you did. 2) Two hand-made servers end up slightly different ("drift"), which causes bugs nobody can explain. 3) The subject demands automation. So the rule for the whole project is: nothing is configured by hand on a server; everything is written in the repo.

Two computers, two roles

  • Control node: your Mac. Ansible, uv and this repo live here. It gives the orders.
  • Targets (managed nodes): the servers. Docker, the firewall and the website live here. They receive the orders over SSH.

Nothing is shared between the two servers. Each one is set up independently from the same manual.

The team

You are Person A: the servers and the secrets (Ansible, firewall, vault, later TLS certificates). Your teammate is Person B: the website itself (Docker Compose files, nginx config, the app role). The two parts meet at variables: her role needs values that you provide. That meeting point is Phase 3A.

4. Phase 0: the tools done

Before writing a manual, make sure everyone works under identical conditions. "It works on my laptop" is not acceptable, especially at the defense, which happens on a different computer.

4.1 uv, pyproject.toml, uv.lock

What: Ansible is a Python program. pyproject.toml is a shopping list ("Python 3.13, ansible-core 2.21.5, pre-commit 4.7.0"). uv downloads exactly that into a private folder (.venv) so nothing mixes with the rest of your Mac. uv.lock is the receipt with the exact versions bought.

WhyDifferent versions behave differently. Pinning every version means you, your teammate and the defense machine get the same behaviour. uv even downloads Python 3.13 itself, so pinning costs nothing.

4.2 ansible-core and requirements.yml

What: We install the small ansible-core instead of the huge ansible package, and list the extra modules we need in requirements.yml: community.docker, community.general, ansible.posix, each with a fixed version. These are called collections.

WhySmaller and explicit: you know exactly what the project depends on. Collections are installed on your Mac; Ansible sends the needed code to the servers over SSH when it runs.

4.3 pre-commit: an automatic proofreader

What: .pre-commit-config.yaml runs checks every time you make a commit. If one fails, the commit is refused.

CheckWhat it catches
trailing-whitespace, end-of-file-fixer, check-yaml, check-added-large-filesSloppy files, invalid YAML, accidentally committed huge files
gitleaksPasswords, tokens and keys. Very important: once a secret enters git history it stays there forever, even if you delete it later
yamllintYAML formatting (indentation, comment spacing)
ansible-lintAnsible bad habits (unnamed tasks, wrong module names ...)

4.4 Makefile and scripts/setup.sh

What: A Makefile is a list of shortcuts. make setup runs scripts/setup.sh, which: detects your OS; installs uv if missing; (with -dev, on a Mac) installs Multipass; runs uv sync --locked (install exactly the locked versions); runs pre-commit install (turn the proofreader on); and installs the Ansible collections.

WhyOne memorable command instead of five long ones, and a new person (or the defense computer) is ready in minutes. The script starts with set -euo pipefail: stop at the first error, treat unset variables as errors, and fail a pipe if any part fails. Without it, a script can fail halfway and still print "success".

make setup = tools only (use this on the defense machine). make setup-dev = tools + Multipass + the practice VMs.

5. Phase 1A: practice servers done

To test a manual that builds a restaurant in an empty building, you need empty buildings. Real servers cost money, so we simulate two on your Mac.

5.1 Multipass VMs (scripts/vms.sh)

What: Multipass creates Ubuntu 22.04 VMs: node1 and node2, each with a 10 GB disk and 1 GB of RAM. The script has three actions, wired to Make: make vms-up (create or start), make vms-down (stop, keep), make vms-destroy (delete completely).

WhyThe real test of the project is "destroy everything, run one command, the site comes back". VMs let you do that in minutes for free. We use Ubuntu 22.04 because that is what the subject assumes. The disk was raised from the default 5 GB because swap plus Docker images did not fit. RAM stays at 1 GB on purpose: it mimics a small cloud instance and forces us to handle low memory properly (swap).

5.2 SSH keys and cloud-init.yml

What: A new server is empty and locked, so how do you get in? With SSH. Passwords can be guessed, so we use key pairs. cloud-init.yml is a note attached to the VM at creation: "when you first wake up, accept these public keys". It contains your public key and your teammate's. Each person generates their own private key at ~/.ssh/cloud1.

WhyThe private key never leaves your Mac and the public key is safe to commit. Cloud providers like AWS use the same cloud-init mechanism, so what you learn transfers directly.

5.3 The inventory (inventory/local.ini)

What: Ansible's address book. It looks like this:

[cloud1]
node1 ansible_host=192.168.x.x
node2 ansible_host=192.168.x.x

cloud1 is the group name; site.yml says hosts: cloud1 to target both servers.

Why generatedThe VM IPs change each time they are recreated, so vms.sh writes the file for you after launching. It is gitignored because it is different on every machine.

5.5 The gate

A gate is a checkpoint that proves a phase works before moving on. For Phase 1A: Ansible could ping both VMs, and a second run reported changed=0.

6. Phase 1B: the app (teammate's part) done

Your teammate built the website stack. You verified it works on Docker Desktop with fake secrets. It lives in roles/app:

  • files/docker-compose.yml: four containers. nginx (the only one exposed to the internet, port 80), wordpress (PHP), mariadb (database) and phpmyadmin. They talk to each other on a private network named internal. Data survives restarts because it is stored in named volumes (wp_data, db_data).
  • templates/nginx/default.conf.j2: the nginx rules. Requests to /phpmyadmin/ require a username and password and are forwarded to phpMyAdmin; everything else goes to WordPress.
  • templates/env.j2: a template for the .env file Docker Compose reads, with the passwords and the phpMyAdmin URL.
  • tasks/main.yml: creates the app folder, copies the compose file, and renders .env with permissions 0600 (only root can read it) and no_log: true (Ansible will not print the secret values in its output).

🎮 Follow a request through the stack

Pick a journey. Notice that the browser only ever talks to nginx.

Why only nginx publishes a portThe database and phpMyAdmin must not be reachable directly from the internet. Everything goes through nginx, which can put a password in front of phpMyAdmin.
Known gaps (to discuss with her) (1) The compose file mounts ./nginx/.htpasswd but no task creates it. (2) No task renders default.conf.j2 into {{ app_dir }}/nginx/default.conf. (3) The nginx file hardcodes /phpmyadmin/ and ignores the pma_path variable.

7. Phase 2A: server roles done

site.yml is the playbook:

- name: Prepare servers
  hosts: cloud1
  become: true        # run as root
  roles:
    - common
    - docker
    - firewall

hosts: cloud1 = both servers. become: true = use root powers (sudo), needed to install software. Roles run top to bottom; the order matters (Docker must exist before the app can run).

Anatomy of a role

  • tasks/main.yml: the steps, loaded automatically by convention.
  • defaults/main.yml: default values for the role's variables (the weakest level; anything else can override them).
  • handlers/main.yml: actions that only run when notified by a task that changed something.
  • templates/ and files/: templated files and plain files to copy.

Naming conventions we follow: variables get the role name as a prefix (common_swap_size), use underscores only, and task names start with an uppercase letter and describe the result ("Swap file is active"), not the action.

7.1 Role common

TaskWhat it doesWhy
Base packagesapt installs curl and ca-certificates; cache_valid_time: 3600 skips refreshing the package list if it was refreshed in the last hourcurl downloads things; ca-certificates lets the server trust HTTPS sites. The cache setting avoids slow, pointless refreshes
SSH runningMakes sure the ssh service is started and enabled at bootIf SSH is not running, you can never reach the server again
SwapImports swap.yml only when swaptotal_mb == 0See below
What is swap?When RAM is full, the operating system moves rarely used data to a file on the disk. That file is swap. It is slow but prevents the kernel from killing processes. With only 1 GB RAM and four containers, it is a safety net. USED 0B is healthy: it means swap exists but is not needed.

🎮 RAM, swap and the out-of-memory killer

Drag the slider: how much memory the containers want. The VM has 1024 MB of RAM.

Swap (the disk file)

swap.yml, step by step:

  1. filesize: create /swapfile of 1 GB with permission 0600 (only root; memory can contain secrets).
  2. filesystem: format it as swap.
  3. mount (state: present): add a line to /etc/fstab, the file listing what the system mounts at boot. This makes swap survive a reboot.
  4. command: swapon: turn it on right now. changed_when: true because the command module cannot know whether anything changed.

The when: on the import makes the whole thing skip on servers that already have swap, which is what keeps reruns at changed=0. Defaults live in defaults/main.yml: common_swap_size: 1G, common_swap_path: /swapfile.

7.2 Role docker

  1. Add Docker's official apt repository (deb822_repository). Ubuntu's own package list has an older Docker; Docker's repo has the current one. The Ubuntu release name (jammy) comes from a fact the server reports about itself, ansible_facts['distribution_release']. register: docker_repo saves the task's result.
  2. Install docker-ce (the background engine), docker-ce-cli (the docker command), containerd.io (low-level runtime) and docker-compose-plugin (adds docker compose). update_cache: "{{ docker_repo is changed }}" refreshes the package list only if the repo was just added.
  3. Start and enable the docker service at boot.
Why deb822_repositoryThe older apt_key and apt_repository modules are deprecated (removed in Ansible 2.25), and get.docker.com is an opaque script. deb822_repository is the modern, declarative way.

7.3 Role firewall

  1. Install ufw.
  2. Allow ports 22, 80, 443 using a loop (one task, three values).
  3. Enable ufw with default policy deny: anything not on the allowed list is blocked.
  4. Disable SSH password login by writing /etc/ssh/sshd_config.d/10-no-password.conf. The validate: sshd -t -f %s line tests the file before it is put in place, so a typo cannot break SSH. notify: Restart ssh triggers the handler.
Order matters: allow first, deny afterIf you enable "deny everything" before allowing port 22, you lock yourself out of your own server. Allow rules always go first.

HandlersA handler runs only if a task that notifies it actually changed something, and only once at the end. SSH is restarted only when the config file really changed. The handler's name must match the notify: text exactly.
Important limitationDocker publishes ports by editing the firewall rules directly, bypassing ufw. That is why only nginx has a ports: entry. The real security perimeter in production will be the cloud provider's firewall (AWS security groups) as well.

7.4 The Makefile targets for deploying

  • make deploy-local → ansible-playbook -i inventory/local.ini site.yml (runs the manual on the VMs).
  • make check-local → same with --check --diff: a dry run that shows what would change without changing it.
  • Both depend on vms-up, so the VMs are guaranteed to be running first.
  • deploy and check (no suffix) are reserved for AWS in Phase 4.

7.5 The gate that passed

make vms-destroy && make deploy-local gave changed=10 (everything built from scratch); a second run gave changed=0 (nothing left to do); ufw was active; SSH password login was refused. That is the whole philosophy working: blank VM + one command = configured server, and re-running is harmless.

8. Phase 3A: variables and secrets in progress

The teammate's app role is code with holes: it says {{ app_dir }}, {{ domain }}, {{ vault_db_password }} but does not define them. Phase 3A fills in those holes. No new servers or tasks are created; we only provide values. Variables are the interface between your work and hers.

The role is the code; the variables are the configuration. That separation lets the same role deploy to your VMs today and to AWS later.

8.2 Where does a value win? (precedence)

The same variable can be defined in several places. Ansible picks by priority, weakest to strongest, for the places we use:

role defaults/main.yml   (weakest: "reasonable default")
   ↓ overridden by
group_vars/all/*         (shared by every server)
   ↓ overridden by
host_vars/<node>.yml     (strongest: specific to one server)

🎮 Who wins? Variable precedence

Tick or untick where common_swap_size is defined. The strongest ticked layer wins.

Role defaults/main.yml (weakest)1G
group_vars/all/vars.yml (all servers)2G
host_vars/node1.yml (strongest, one server)4G

Why this designA role ships sensible defaults, the project overrides them for all servers, and a single server can still differ. Ansible loads every file in group_vars/all/ and merges them, so splitting plain and secret values into two files costs nothing.

8.3 Why a vault, and how it works

Passwords must be in the repo (the deploy has to be reproducible from git), but a plaintext password in git is a disaster. Ansible Vault encrypts a file so the repo holds only unreadable text. Ansible decrypts it in memory at deploy time using a password stored in a local file, .vault_pass, which is gitignored and shared between you and your teammate only in person or through a password manager.

  • vars.yml stays plain: readable, diff-able in pull requests.
  • vault.yml is encrypted and contains only secrets.
  • gitleaks (Phase 0) is the second safety net: if you ever stage a plaintext secret by mistake, the commit is blocked.

8.4 Why certificates are trustworthy (and why staging exists)

Anyone can create and sign a certificate, but a self-signed one gives a scary browser warning. Browsers ship with a built-in list of trusted Certificate Authorities (CAs), and trust only certificates signed by one of them. A CA such as Let's Encrypt signs only after you prove you control the domain: it asks you to publish a specific file at http://yourdomain/.well-known/... and checks it can fetch it. So you cannot get a certificate for a domain you do not control, and a certificate is useless for any other domain.

The Let's Encrypt staging server follows the same process but signs with a CA that browsers do not trust, so mistakes while developing cannot get you rate-limited on the real one. This is why the TLS role will need: the domain's DNS pointing at the server, and port 80 open (our firewall already allows it).

11. Gotchas we hit

  • make lint only checks tracked files: git add new files before linting.
  • The commit hook checks the staged copy: after fixing a file, git add it again.
  • On a Spanish Mac keyboard, # is Option+3, and Option+Space types a non-breaking space, which yamllint reports as "missing starting space in comment".
  • --check on a brand-new VM can fail (the Docker repo was not really added in a dry run, so docker-ce "is not found"). Use --check on already-deployed hosts.
  • An ad-hoc -a "command" always shows CHANGED, because the command module cannot know.
  • when: takes a bare expression, with no {{ }}.
  • notify: must match the handler's name exactly.
  • Variable names: role prefix, underscores only (no hyphens). Task names start uppercase.

13. Explain it back (self-test)

You understand something when you can explain it without looking. Read the question, answer out loud, then open the answer and compare.

The 60-second pitch "The subject wants a WordPress site that deploys itself onto an empty Ubuntu server with one command. I wrote the manual in Ansible: a playbook that runs roles in order. common installs basics and swap, docker installs Docker from the official repo, firewall opens only ports 22, 80 and 443 and disables password logins. My teammate's app role copies the Docker Compose stack. Values like the domain and the passwords are not in the roles: plain ones live in group_vars and host_vars, secrets are encrypted with Ansible Vault. Every task describes a desired state, so running it twice changes nothing, and I tested that on two Multipass VMs by destroying them and redeploying."
1. Why Ansible instead of logging in and typing commands?

Hand-made servers cannot be reproduced and drift apart. A written manual is repeatable, reviewable in git and testable: destroy the VM, run one command, get the same server.

2. What is the control node and what are the targets?

The control node is your Mac: it has uv, Ansible and the repo, and gives the orders. The targets are the servers: they hold Docker, the firewall and the website, and receive the work over SSH. Nothing is shared between the servers.

3. What does "idempotent" mean, and how did you prove it?

Running it again gives the same end state and changes nothing. Tasks describe a result ("swap is configured"), not an action. The proof was the second run reporting changed=0.

4. How does SSH key login work and why disable passwords?

The server holds your public key (put there by cloud-init). It challenges you; your Mac signs with the private key, which never leaves it; the server verifies with the public key. Passwords can be guessed, keys cannot realistically, so the firewall role turns password login off.

5. In the docker role, why register: docker_repo and update_cache: "{{ docker_repo is changed }}"?

After adding a new apt repository you must refresh the package list, otherwise docker-ce is "not found". But refreshing on every run is slow and pointless. register saves the repo task's result, and the cache refresh happens only when that task actually changed something.

6. Why does the firewall allow ports first and enable "deny" after?

A default-deny policy with no allow rule for port 22 refuses new SSH connections, so you lock yourself out and the playbook can never finish. Specific allow rules always beat the default policy, so they must exist first.

7. What is swap, and why is the swap import wrapped in a when:?

Swap is a disk file the kernel uses as spare RAM, so a 1 GB VM running four containers is not killed when memory fills. The when: swaptotal_mb == 0 skips the whole swap file when the VM already has swap, which keeps reruns at changed=0.

8. What is a handler and why is Restart ssh one?

A handler runs only if a task that notifies it changed something. SSH is restarted only when the config file really changed, not on every run.

9. Role defaults vs group_vars vs host_vars: which wins?

Role defaults are weakest, group_vars/all overrides them for every server, host_vars/<node> overrides both for one server. That lets a role ship reasonable defaults while the project (or one machine) still decides.

10. Why a vault, and what is the vault_ prefix?

The deploy must be reproducible from git, but plaintext passwords in git are a disaster. Ansible Vault encrypts the file; the password lives in a gitignored .vault_pass. The prefix tells a reader "this value comes from the encrypted file". gitleaks is a second net that blocks plaintext secrets at commit time.

11. Why does only nginx publish a port?

The database and phpMyAdmin must not be reachable from the internet directly. Everything enters through nginx, which can also put a password in front of phpMyAdmin. (Docker bypasses ufw for published ports, so the fewer published, the safer.)

12. Why keep le_staging: true for now?

The Let's Encrypt test server signs untrusted certificates but has generous rate limits. While you rebuild VMs and make mistakes, you cannot get blocked on the real one. Switch to false only for the final deploy.

13. Why is pma_path only /phpmyadmin?

The template builds the URL as http://{{ domain }}{{ pma_path }}. The host belongs to domain (it differs per server), the path belongs to pma_path. Putting the host in the path would produce a broken URL; try it in the template demo above.
